- **Data-quality defects:** `locality` contains the value `real` in 18 rows (a shifted `source_type` value in the wrong column); `district` is constant, so it carries no information.
- **Duplicates:** {'raw_text': 9, 'normalized_text': 23, 'english_gloss': 42, 'english_gloss_after_normalisation': 44}. Urgency-conflicting duplicate-text groups: 1. Cross-split gloss overlap: {'train&val': 9, 'train&test': 5, 'val&test': 4} (train/val/test leakage).
- **Target leakage risk:** `urgency` is 78% predictable from `severity` alone and 79% from `intent`+`severity`. Those columns are label-like and are **excluded from the features**; the model sees text only. Consequence: what the model can learn is essentially 'does this text read like an information query / hazard / delay', i.e. the severity/intent structure expressed in words.

## Suitability verdict

- A usable 3-class urgency target exists and is internally consistent enough to train on (conflicting duplicates are rare).
- **It is not railway data.** There are no railway complaints, no `critical` examples, and the only English text is a short translation gloss. Offline metrics therefore describe in-domain performance on Chennai civic requests and say little about RailResolve complaints. The trained model should be treated as an experimental advisory signal until it is validated on labelled railway complaints.
- Test (60) and validation (60) sets are small; the `low` class has very few examples in each, so per-class metrics carry wide uncertainty (confidence intervals are reported with the evaluation).
